\title{
  \textbf{Functional Versus Imperative Is Solved}\\[0.2em]
  \large Power, Cost, and Shared State in the Paradigm Debate
}
\author{}
\date{29 October 2026}

\begin{document}
\maketitle

\begin{abstract}
  Functional and imperative programming are usually argued about as
  matters of taste. We instead treat the argument as a set of questions
  with known answers, most of them proved by someone else first. (i) The
  two styles compute exactly the same functions, as Turing and Kleene
  established by 1937, so no program can be written in one and not the
  other. (ii) Compilers translate between them routinely: the SSA form
  inside Clang and GCC can be read as a functional program, and GHC
  implements lazy
  evaluation by overwriting memory. (iii) For Pippenger's symbolic
  on-line programs, purity costs at most a logarithmic factor in time,
  some problems pay exactly that factor when nothing is evaluated lazily,
  and Bird, Jones and de Moor showed that laziness removes it from the
  known example, through a write-once mutation that no program can
  observe. (iv) A data race needs a location that is both shared and
  mutable (\emph{Share or Mutate}). Functional programming forbids the
  mutation and Rust forbids sharing what is being mutated, while linear
  types and reference counting let pure languages update unshared values
  in place, so the two styles have reached the same rule from opposite
  ends. (v) Each style makes some changes local by making others global,
  the Expression Problem among them. A review of the evidence finds the
  effect of language on defects small and fragile, controlled
  experiments on readability split, and energy use varying by a factor of
  77 within the languages one study classes as functional. Meanwhile the
  languages converged: imperative ones adopted lambdas, streams and
  pattern matching, and Haskell is, in the words of one of its designers,
  the world's finest imperative programming language.
\end{abstract}

\section{Two Ways to Sum a List}\label{sec:defs}

Here is the same function written twice.

\noindent
\begin{minipage}[t]{0.5\textwidth}
  \begin{lstlisting}[language=C, caption={Imperative, in C.}, label=lst:c]
int total(const int *xs, int n) {
  int acc = 0;
  for (int i = 0; i < n; i++)
    acc += xs[i];
  return acc;
}
  \end{lstlisting}
\end{minipage}%
\begin{minipage}[t]{0.5\textwidth}
  \begin{lstlisting}[language=Haskell, caption={Functional, in Haskell.}, label=lst:hs]
total :: [Int] -> Int
total []       = 0
total (x : xs) = x + total xs
  \end{lstlisting}
\end{minipage}

\medskip
\noindent The first is a list of instructions. The second is a pair of
equations. Programmers have argued about which is better for most of the
history of programming, and the argument is older than most of the
languages it is now conducted in. We settle it.

\begin{definition}[Imperative]
  A program is \emph{imperative} if its meaning is a sequence of
  commands, each of which changes a \emph{store}, a map from locations to
  values. Running it executes the commands in order, and its result is
  read from the final store.
\end{definition}

\begin{definition}[Functional]
  A program is \emph{functional} if its meaning is an expression, and the
  meaning of an expression is its value. It is \emph{pure} if the value
  of every expression depends only on the values of its subexpressions,
  so that any subexpression can be replaced by its value without changing
  the meaning of the whole. Strachey, borrowing from Quine, called this
  property \emph{referential transparency}~\cite{strachey}.
\end{definition}

\begin{remark}
  The term has since been used in several senses that are not
  equivalent~\cite{sondergaard}. We use Strachey's. Both definitions
  classify programs, not languages. C permits a function that assigns
  nothing, and Haskell permits one that does nothing but assign. Most
  languages in use permit both, so the question is not which language to
  use but which kind of program to write.
\end{remark}

The debate concerns four questions, which we take in turn: whether one
style can compute more than the other (Section~\ref{sec:power}), say
more (Section~\ref{sec:express}), run faster (Section~\ref{sec:cost}),
or go wrong less often (Sections~\ref{sec:shared}
and~\ref{sec:evidence}). Section~\ref{sec:both} shows that compilers
already translate between the styles, Section~\ref{sec:convergence} that
the languages have converged, and Section~\ref{sec:main} states the
result.

\section{The Ceasefire of 1937}\label{sec:power}

The first question, whether one style can compute something the other
cannot, was settled before either had a machine to run on. Church
proposed that the effectively calculable functions are those definable
in the $\lambda$-calculus~\cite{church}. Turing proposed those computable
by a machine that reads and writes symbols on a tape, following a table
of instructions~\cite{turing36}. The first is a functional language and
the second an imperative one.

\begin{theorem}[The Church--Turing Ceasefire]\label{thm:ceasefire}
  A function on the natural numbers is $\lambda$-definable if and only if
  it is computable by a Turing machine.
\end{theorem}

\begin{proof}
  Turing showed that every $\lambda$-definable function is computable and
  every computable function is general recursive~\cite{turing37}, and
  Kleene that every general recursive function is
  $\lambda$-definable~\cite{kleene}.
\end{proof}

\begin{corollary}[No Exclusive Programs]\label{cor:exclusive}
  Any function computed by a program in one Turing-complete language,
  functional or imperative, is computed by some program in any other.
\end{corollary}

\begin{proof}
  Each such language computes at least the functions that Turing machines
  compute, since it is Turing-complete, and at most these, since a Turing
  machine can run its interpreter. Theorem~\ref{thm:ceasefire} is the
  case of the $\lambda$-calculus and Turing's machines.
\end{proof}

\begin{remark}
  The ceasefire was signed in 1937, eleven years before the first
  stored-program computer ran a program~\cite{baby}. It concerns which
  functions can be computed, not how quickly, how clearly, or how often
  incorrectly. The rest of this paper is about those.
\end{remark}

\section{Every Program Is Both}\label{sec:both}

The ceasefire is not only a theorem. Compilers carry it out, in both
directions, on most programs that are ever run.

\begin{proposition}[Lambda, the Ultimate Goto]\label{prop:goto}
  A call in tail position, whose result the caller returns unchanged, can
  be compiled as a jump that reuses the caller's stack frame. A
  tail-recursive function therefore runs as a loop, in constant stack
  space~\cite{steele77}.
\end{proposition}

A functional programmer who wants the loop of Listing~\ref{lst:c} writes
Listing~\ref{lst:go}, which GHC compiles to a loop.

\begin{lstlisting}[language=Haskell, caption={Listing~\ref{lst:c}, as a
  functional programmer writes it.}, label=lst:go]
total :: [Int] -> Int
total xs = go xs 0
  where
    go []       acc = acc
    go (y : ys) acc = go ys (acc + y)
\end{lstlisting}

\begin{proposition}[SSA Is Functional Programming]\label{prop:ssa}
  In \emph{static single assignment} (SSA) form every variable is
  assigned exactly once, and where control flow merges, a
  $\phi$-function selects a value according to the block that control
  came from~\cite{cytron}. A program in SSA form can be read as a
  functional program:
  each block is a function, each $\phi$-function a parameter, and each
  jump a tail call~\cite{appel,kelsey}.
\end{proposition}

\noindent
\begin{minipage}[t]{0.5\textwidth}
  \begin{lstlisting}[caption={Listing~\ref{lst:c} in SSA form.},
    label=lst:ssa]
entry:
  br loop
loop:
  i   = phi [0, entry], [i1, body]
  acc = phi [0, entry], [acc1, body]
  br i < n, body, exit
body:
  acc1 = acc + xs[i]
  i1   = i + 1
  br loop
exit:
  ret acc
  \end{lstlisting}
\end{minipage}%
\begin{minipage}[t]{0.5\textwidth}
  \begin{lstlisting}[caption={Listing~\ref{lst:ssa}, read as functions.},
    label=lst:fun]
entry()      = loop(0, 0)
loop(i, acc) = if i < n then body(i, acc)
               else exit(acc)
body(i, acc) = loop(i + 1, acc + xs[i])
exit(acc)    = acc
  \end{lstlisting}
\end{minipage}

\medskip
Clang compiles C to LLVM IR, which is in SSA form
throughout~\cite{llvm}, and the \texttt{mem2reg} pass promotes local
variables whose addresses are never taken out of memory and into SSA
form~\cite{mem2reg}. GCC has optimised in SSA form since version 4.0, in
2005~\cite{gcc4}. Arrays and other memory remain loads and stores, so
Appel's reading covers the scalar variables~\cite{appel}, but the loop of
Listing~\ref{lst:c} spends most of its time in the compiler as the
functions of Listing~\ref{lst:fun}. C programmers have been writing
functional programs for decades. The compiler was too polite to mention
it.

The traffic runs the other way too. GHC translates Haskell through two
functional intermediate languages, Core and STG, into Cmm, ``a low-level
imperative language with an explicit stack'', and from there into
machine code, directly or through LLVM~\cite{ghc}. Lazy evaluation, which
in the words of Haskell's designers ``kept us pure''~\cite{history}, is
itself implemented by mutation. An argument is passed unevaluated, as a
\emph{thunk}, and the first time its value is needed the thunk is
overwritten in place with that value, so that it is computed at most
once. Wadsworth proposed this in 1971~\cite{wadsworth}, and GHC's STG
machine works this way~\cite{stg}.

\section{Equally Powerful, Not Equally Expressive}\label{sec:express}

Corollary~\ref{cor:exclusive} allows a translation to rewrite the whole
program, which is how compilers use it. Programmers would rather not.
Felleisen asked instead which features can be removed by \emph{macro}
translation, rewriting each use of a feature from its parts without
touching the rest of the program~\cite{felleisen}. His test is
observational: if a new feature lets some program tell apart two
expressions that no program could tell apart before, no macro can remove
it.

\begin{theorem}[Felleisen]\label{thm:felleisen}
  In Pure Scheme, a call-by-value functional language, the expressions
  \code{((lambda (d) (f 0)) (f 0))} and \code{(f 0)}, which
  call \code{f} twice and once, are operationally equivalent.
  Assignment, through \code{set!} and \code{letrec}, separates
  them, so Pure Scheme cannot macro-express assignment~\cite{felleisen}.
\end{theorem}

\begin{proof}[Sketch]
  Without assignment, a function called twice on the same argument does
  the same thing both times, so the first call can matter only by never
  returning, and then the single call never returns either. With
  assignment, \code{f} can redefine itself on its first call so that
  its second call never returns.
\end{proof}

Felleisen proves the same for first-class continuations. The theorem's
witness is a familiar maintenance problem. Suppose a function deep
inside a pure program must now count how often it is called, which is
exactly the difference between calling it twice and calling it once. In
C this is one global variable and one increment. In Haskell the
function's type changes, from \code{a~->~b} to
\code{a~->~State~Int~b}, and so does the type of every function that
calls it, directly or not. The imperative programmer pays the same price
elsewhere. Keeping the previous version of a data structure, to undo an
edit or to read it from another thread, is free in a pure program, where
old versions are never destroyed, and needs a copy before every update,
or a redesigned structure~\cite{dsst}, in an imperative one.
Table~\ref{tab:changes} collects these and two more.

Wadler named the last two rows the \emph{Expression Problem}: to define
a data type by cases, ``where one can add new cases to the datatype and
new functions over the datatype, without recompiling existing code, and
while retaining static type safety''~\cite{expression}. Solutions exist,
and rely on type-system features developed for the
purpose~\cite{swierstra}.

\begin{remark}[Conservation of Inconvenience]
  For changes that cross function boundaries, each style makes some local
  by making others global. Felleisen's measure ranks languages, not
  styles, and it rewards having everything: any feature that no macro can
  remove makes a language more expressive, which may explain C++.
\end{remark}

\section{The Price of Purity}\label{sec:cost}

A pure program cannot update memory in place. Where C overwrites one
element of an array, a pure program builds a new array, or a new path
through a tree that shares everything else with the old one. Pippenger
asked what this costs, in a model of Lisp in which purity means giving
up \code{rplaca} and \code{rplacd}, the operations that overwrite a cons
cell~\cite{pippenger}. His programs are \emph{on-line}, producing each
output before reading the next input, and \emph{symbolic}, comparing
input symbols only for equality.

\begin{proposition}[The Logarithm Bound]\label{prop:logbound}
  An impure symbolic on-line program that performs $T$ operations can be
  simulated by a pure one that performs $O(T\log T)$~\cite{pippenger}.
\end{proposition}

\begin{proof}
  Keep the cells that the impure program overwrites in a balanced tree,
  keyed by when they were created, and copy the path to a cell when it is
  updated. With at most $T$ cells the tree has depth $O(\log T)$, so each
  access costs $O(\log T)$, and each new version of the tree shares all
  but one path with the old.
\end{proof}

\begin{theorem}[Pippenger]\label{thm:pippenger}
  There is a symbolic on-line problem that an impure Lisp program solves
  with $O(n)$ operations, while every pure Lisp program needs
  $\Omega(n\log n)$ operations on some inputs~\cite{pippenger}.
\end{theorem}

The logarithm is therefore sometimes charged, in a model that evaluates
everything as soon as it can. Lazy evaluation changes the answer.

\begin{theorem}[Bird, Jones and de Moor]\label{thm:bird}
  With lazy evaluation, a pure program solves Pippenger's problem in
  linear time overall~\cite{bird}.
\end{theorem}

\begin{remark}[The Refund]
  Laziness recovers the logarithm through the mechanism of
  Section~\ref{sec:both}: an evaluated thunk is overwritten with its
  value. Bird, Jones and de Moor call this ``essentially a restricted
  memoization'', and the capsule review printed with their paper calls it
  ``this restricted form of mutation''. They ``do not, and cannot, claim
  that a lazy implementation can solve all problems with the same
  efficiency as an impure Lisp solution''~\cite{bird}, and as far as we
  know the question is still open. Purity costs at most a logarithm, and
  on the problem that shows the logarithm is ever charged, laziness
  refunds it.
\end{remark}

Many structures pay nothing (Table~\ref{tab:costs}).
Hood and Melville gave a purely functional queue whose every operation
takes constant time in the worst case~\cite{hood}. Okasaki's simpler one
relies on laziness, and he concedes that ``some might argue that our
implementation is not, in fact, purely functional because of the
imperative nature of memoization''~\cite{okasaki95}. Persistence, the
ability to read old versions after an update, comes free with purity,
and costs an imperative linked structure of bounded in-degree $O(1)$
amortised time and space per update~\cite{dsst}.

    \midrule

\section{Share or Mutate}\label{sec:shared}

The strongest argument for functional programming concerns concurrency.

\begin{definition}[Data race]\label{def:race}
  A \emph{data race} is a pair of accesses to the same memory location
  by different threads, at least one of them a write, that are not
  ordered by synchronisation.
\end{definition}

\begin{proposition}[Share or Mutate]\label{prop:share}
  A data race needs a location that is both \emph{shared}, accessed by
  two threads, and \emph{mutable}, written by at least one of them. A
  program in which no location is both has no data races.
\end{proposition}

\begin{proof}
  Definition~\ref{def:race}.
\end{proof}

Concurrency bugs in practice look like this. Lu et al.\ sampled 105 from
MySQL, Apache, Mozilla and OpenOffice. Of these, 74 did not involve
deadlock, and 72 of those were atomicity or order violations, in which
accesses to memory shared between threads happened in an order the
programmer had not intended~\cite{lu}.

A pure program writes nothing once a value is built, so it has no data
races, and its parts can be evaluated in any order, or at once, without
changing its result. For the $\lambda$-calculus this is a theorem.

\begin{theorem}[Church--Rosser]\label{thm:cr}
  If a $\lambda$-term reduces to two terms, then both reduce to a common
  term. In particular a term has at most one normal form, whatever order
  its reductions are performed in~\cite{churchrosser}.
\end{theorem}

Permission to evaluate in parallel is not a speedup. If a fraction $f$ of
a program's work can be spread over $p$ processors and the rest cannot,
the speedup is at most
\begin{equation}
  S(p) = \frac{1}{(1-f) + f/p} < \frac{1}{1-f},
\end{equation}
a bound now called Amdahl's law after his argument in~\cite{amdahl}. A
program that is 90\% parallel runs at most ten times faster, on any
number of processors, in either style.

Imperative languages can remove the sharing instead of the mutation. In
Rust, ``at any given time, you can have either one mutable reference or
any number of immutable references'', and because the compiler enforces
this, ``Rust can prevent data races at compile time''~\cite{rustbook}.
RustBelt proved the discipline sound for a formal model of the language,
including libraries that use unsafe code inside: a well-typed program
``will not have data races''~\cite{rustbelt}.

Pure languages, from the other side, have learned to mutate what is not
shared. Values of a linear type ``must be used exactly once'', and so
``safely admit destructive array update''~\cite{wadler90}. GHC has
supported linear types since version 9.0~\cite{linearhaskell,ghc9}.
Perceus, the reference counting of the Koka language, checks at run time
whether a reference is unique, ``to update in-place when
possible''~\cite{perceus}.

\begin{tcolorbox}[colback=white, colframe=black!50, boxrule=0.5pt]
  \textbf{Remark (The Paradigm War, Stated Precisely).}
  Proposition~\ref{prop:share} is the rigorous content of the debate. The
  hazard was never mutation, and never sharing, but the two at once.
  Functional programming forbids mutation, and pays for it in
  Section~\ref{sec:cost}. Rust forbids sharing while mutating, and pays
  in annotations and a borrow checker. Linear types let pure programs
  mutate what is unshared, and ownership lets imperative programs share
  what is immutable, so the two paradigms have reached the same rule from
  opposite ends.

  \begin{center}
    \bfseries Share or mutate. Not both.
  \end{center}
\end{tcolorbox}

\section{What the Evidence Says}\label{sec:evidence}

Theorems settle what is possible. Whether either style produces better
programs in practice is an empirical question, and the evidence is
thinner than the debate.

The largest study of defects, by Ray et al., modelled bug-fixing commits
in 729 GitHub projects written in 17 languages, with 80 million lines of
code and 1.5 million commits. It found ``a small but significant
relationship between language class and defects'', with functional
languages doing better than procedural or scripting ones. Language
accounted for less than one percent of the deviance, and the authors
warned that even this might reflect ``the preference of certain
personality types for functional, static and strongly typed
languages''~\cite{ray}. A reproduction by Berger et al. found flaws in
the data and the analysis, including a false-positive rate of 36\% among
the commits labelled as bug fixes. After correcting them, the number of
languages associated with defects fell from eleven to four: C++ with
more, and Clojure, Haskell and Ruby with fewer, all by amounts the
authors call ``exceedingly small''. Causation, they add, ``is not
supported by the data at hand''~\cite{berger}. A Bayesian reanalysis of
the same data concluded that the question ``does not admit a simple,
generally valid answer''~\cite{furia}.

Controlled experiments are smaller, and they split. Uesbeck et al.\ had
54 programmers, from first-year students to professionals, solve tasks
in C++ with either lambdas or an iterator class. The lambda group took
longer and made about twice as many compiler errors, and there was no
benefit from lambdas at any level of experience, professionals included,
though the authors suspect a novelty effect~\cite{uesbeck}. Mehlhorn and
Hanenberg had 20 programmers read Java code that processed collections
with loops or with streams. With loops they needed 78\% more time and
gave three times as many wrong answers~\cite{mehlhorn}. One study
measured writing and the other reading, and the functional style lost
the first and won the second. Pankratius et al.\ had 13 programmers write
the same projects in both Scala and Java. The Scala code was shorter, but
the study refuted Scala's claims of lower programming and debugging
effort~\cite{pankratius}.

Speed and energy depend on the implementation more than on the style.
Pereira et al.\ ran programs for the same benchmark problems in 27
languages and measured their energy, time and memory~\cite{pereira}.
Averaged over the authors' classes of paradigm, imperative languages
used 125~J and functional ones 1,367~J. The classes overlap, however, and
the functional class, which includes Rust and Perl, spans a factor of 77,
from 1.03 times the energy of C to 79.58 (Figure~\ref{fig:energy}). Of
that class's total, 90\% comes from Erlang, Ruby and Perl, which run on a
virtual machine or an interpreter. The compiled functional languages
OCaml and Haskell used 2.40 and 3.10 times the energy of C, close to Go
at 3.23 and C\# at 3.14.

Two landmark verified systems sit on the border. CompCert is a C compiler
programmed in Coq, which serves as both its programming language and the
proof assistant that verifies it, and extracted to Caml~\cite{leroy}.
Testing compilers with random C programs, Yang et al.\ reported more
than 325 previously unknown bugs, and of CompCert wrote that ``the
middle-end bugs we found in all other compilers are absent''. As of early
2011 it was ``the only compiler we have tested for which Csmith cannot
find wrong-code errors''; the bugs they did find were in its unverified
front end~\cite{csmith}. The seL4 kernel is 8,700 lines of C and 600 of
assembler, proved correct with 200,000 lines of proof script in
Isabelle/HOL. Its designers
wrote it first as a Haskell prototype, translated that into the prover
as an executable specification, and then reimplemented it by hand in
C~\cite{sel4}. CompCert is a functional program that compiles imperative
ones, and seL4 an imperative program designed in a functional language.

\section{Convergence}\label{sec:convergence}

While the debate continued, the languages settled it.
Table~\ref{tab:convergence} lists when imperative languages acquired the
features once used to define functional programming, and when functional
languages acquired the means to mutate.

\begin{table}[ht]
  \centering
  \begin{tabular}{@{}lll@{}}
    \toprule
    Year & Language & Acquired \\
    \midrule
    \multicolumn{3}{@{}l}{\emph{Imperative languages}} \\
    1995 & JavaScript & first-class functions~\cite{js} \\
    2007 & C\# 3.0 & lambda expressions, query expressions~\cite{csharp} \\
    2011 & C++11 & lambda expressions~\cite{cpp11} \\
    2014 & Java 8 & lambda expressions, streams~\cite{jdk8} \\
    2015 & Rust 1.0 & algebraic data types, immutability by
    default~\cite{rustbook,rust1} \\

    2023 & Java 21 & pattern matching for \texttt{switch}~\cite{jdk21} \\
    \addlinespace
    \multicolumn{3}{@{}l}{\emph{Functional languages}} \\
    1990 & Standard ML & mutable reference cells~\cite{sml} \\

  \end{tabular}

Haskell, which is purely functional, is in the words of one of its
designers ``the world's finest imperative programming
language''~\cite{awkward}. It performs input and output through
monads~\cite{moggi,imperative}, and a monad, in Mac Lane's words, ``is
just a monoid in the category of endofunctors''~\cite{maclane}. Readers who
found this helpful may skip the rest of the paragraph. A monad lets a
pure program describe a sequence of effects as a value, which the
runtime then performs, so that the program stays pure and the computer
still does something.

Conversion runs in both directions. John Backus led the group that
produced Fortran~\cite{fortran}, and in his 1977 Turing Award lecture
asked whether programming could be liberated from the von Neumann
style~\cite{backus}. Hughes noted that functional programming is usually
advertised by what it lacks, such as assignment and side effects: ``The
functional programmer sounds rather like a medieval monk, denying himself
the pleasures of life in the hope that it will make him virtuous.'' Since
``it is a logical impossibility to make a language more powerful by
omitting features, no matter how bad they may be'', he located the
advantage elsewhere, in two kinds of glue, higher-order functions and
lazy evaluation, which make programs more modular~\cite{hughes}.
Corollary~\ref{cor:exclusive} agrees about the omission, and
Table~\ref{tab:convergence} shows the imperative languages agreeing
about the glue, or at least the first kind.

There is a precedent. Böhm and Jacopini showed that any flowchart can be
rewritten without jumps, using a few structured forms and some extra
variables~\cite{bohm}, so removing the jump costs no power, and Dijkstra
argued that removing it adds clarity~\cite{dijkstra}. Hughes drew the
same analogy and the same conclusion: what made structured programs
better was their modularity, not their lack of gotos~\cite{hughes}.
Structured programming removed the jump, and functional programming the
assignment. We leave the next removal to future work.

\section{Main Result}\label{sec:main}

\begin{theorem}[Functional Versus Imperative Is Solved]\label{thm:main}
  For programs in Turing-complete languages:
  \renewcommand{\labelenumi}{(\alph{enumi})}
  \begin{enumerate}
    \item the two styles compute exactly the same functions;
    \item compilers translate between them in both directions, and a
      program compiled through SSA form is, for a while, functional;
    \item for symbolic on-line programs, purity costs at most a
      logarithmic factor in time, some problems pay exactly that factor
      when nothing is evaluated lazily, and laziness removes it from the
      known example;
    \item a data race needs a location that is both shared and mutable,
      so pure programs, and imperative programs that forbid shared
      mutation, have none;
    \item for the changes of Table~\ref{tab:changes}, each style makes
      local what the other makes global.
  \end{enumerate}
  No statement in (a)--(e) favours either style unconditionally.
\end{theorem}

\begin{proof}
  Corollary~\ref{cor:exclusive}, Propositions~\ref{prop:goto},
  \ref{prop:ssa}, \ref{prop:logbound} and~\ref{prop:share},
  Theorems~\ref{thm:pippenger} and~\ref{thm:bird}, and
  Table~\ref{tab:changes}.
\end{proof}

\begin{remark}[Interpretation]
  Section~\ref{sec:evidence} adds what the theorems cannot: the measured
  effect of the style on defects is small and fragile, experiments on
  readability point both ways, and energy use varies by a factor of 77
  within the languages one study classes as functional.
  Section~\ref{sec:convergence} records that the languages stopped
  waiting for the debate. The question was never which style to use, but
  which guarantees a program needs, and what it will make inconvenient to
  get them.
\end{remark}

\section{Conclusion}

Functional versus imperative reduces to a list of trades with known
prices. The styles are equal in power (Theorem~\ref{thm:ceasefire}) and
are translated into each other by optimising compilers
(Section~\ref{sec:both}). Purity costs at most a logarithm in
Pippenger's model (Section~\ref{sec:cost}), which laziness refunds on
the known example
through a mutation no program can observe. Data races need shared
mutable state, and functional programming
removes the mutation while Rust removes the sharing
(Section~\ref{sec:shared}). The evidence of Section~\ref{sec:evidence}
finds the style's effect on defects small and fragile, its effect on
readability mixed, and its effect on energy smaller than that of an
interpreter. The languages, meanwhile, have converged
(Section~\ref{sec:convergence}). Open problems include whether a lazy
pure language is ever asymptotically slower than an impure one, and how
either style reads in programs longer than the snippets used in
experiments.
